02 How AES-256-GCM locks the file

The encryption at the heart of the tool. One primitive does both jobs: it hides the bytes and proves nobody touched them.

AES is a symmetric cipher — the same secret key both locks and unlocks the data. It works on fixed 128-bit blocks, and the 256 is the key length in bits (a 32-byte key). A 256-bit key has 2256 possibilities, far beyond brute force. GCM (Galois/Counter Mode) is the mode that turns that block cipher into authenticated encryption: alongside the ciphertext it computes a 16-byte authentication tag that acts like a tamper-evident seal.
🔑

Key — 256 bits

A fresh 32-byte random key per file, from Go's crypto/rand. Never a password. By default the key is stored in the trailer. With --c2-url, it is sent to a remote key server instead.

crypto/rand (32 bytes)
🎲

Nonce — 96 bits

A one-time random number used once per encryption. Reusing a nonce with the same key would break GCM — so a new one is drawn every time.

crypto/rand (12 bytes)
🏷️

Tag — 128 bits

Computed over the ciphertext. On decryption it is re-checked: a wrong key or a single flipped byte makes it mismatch and decryption is refused.

gcm.Open → error
🧷

AAD — the magic

The HBX1 magic is fed in as associated data: authenticated but not encrypted. Edit the magic and the tag check fails.

gcm.Seal(nil, nonce, data, []byte("HBX1"))
In one line: ciphertext = AES-256-GCM(key, nonce, file, aad="HBX1"), and recovery needs the key, the nonce and an intact tag — otherwise it fails loudly instead of returning wrong data.

06 The four stealth moves

Each maps to a concrete part of the Go source code.

🔒

Encrypt

AES-256-GCM scrambles the file with a fresh random key. Wrong key = fails, loudly.

encryptAndBuild() · encrypt.go
📦

Inflate

Zero padding grows the file to an exact size. Big, bland files resist inspection.

writePadding() · encrypt.go
⏱️

Delay

A pre-execution wait. Many sandboxes time out before it ends and see nothing.

metadata.Delay · time.Sleep · runner.src
🎁

Self-extract

By default the key is in the trailer. With --c2-url, the runner fetches the key from a remote server at runtime — no key in the file.

runner.src (embedded, cross-compiled)
Defender's takeaway: size and timing alone can blind signature and sandbox scanners — which is exactly why modern defense watches behaviour at runtime, not just the file.

07 C2 Key Server mode

With --c2-url, the AES key is sent to a remote server at encryption time and fetched by the runner at execution time. The file contains only a key_id — no key, no nonce.

📡

Encrypt → POST key

At build time, the tool sends the key to the C2 server and stores only a key_id reference in the metadata.

encrypt.go → sendKeyToServer()
🔑

Run → GET key

At runtime, the runner calls GET /keys/{id} to fetch the key before decryption. No server = no decryption.

runner.src → fetchKeyFromServer()
🔥

Burn-after-reading

Start the server with --burn: each key is deleted after the first fetch. The binary works exactly once.

keyserver --burn
🔄

Backward compatible

Without --c2-url, the key stays in the file as before. Existing binaries still work unchanged.

metadata.Key fallback
C2 flow: encrypt --c2-url http://server:8080 → key goes to server → file has key_id only → runner calls GET /keys/{id} → decrypts → executes payload.
